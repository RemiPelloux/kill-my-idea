# Pelloux Guidelines

Coding discipline for this project. Mandatory for every human and every AI agent working on it.
Generated by [kill-my-idea](https://github.com/RemiPelloux/kill-my-idea) `build`; edit it to fit
your team, but keep it short.

---

## 1. Think Before Coding

- State assumptions explicitly. If uncertain, ask.
- Surface multiple interpretations; do not pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop and ask.

### Pick the simplest fix (mandatory for non-trivial work)

Before writing code, consider **at least three** plausible approaches (brief is fine):

1. **Fix at the failure point:** widen validation, one-line config, correct the bad assumption.
2. **Workaround elsewhere:** caller-side transform, extra flag, adapter shim.
3. **New pipeline or abstraction:** new module, new base class, shared helper used once.

**Default to (1)** unless a lighter option cannot fully solve the request. If you choose (2) or
(3), state in one sentence why (1) was rejected.

## 2. Simplicity First

- Minimum code that solves the problem. Nothing speculative.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that was not requested.
- No error handling for impossible scenarios.
- 200 lines that could be 50? Rewrite.
- Prefer the standard library and zero-config tools. Every dependency must earn its place;
  record why in `docs/decisions.md`.

## 3. Surgical Changes

- Touch only what the task (the current user story) requires.
- Do not "improve" adjacent code unless asked.
- Match the patterns already used in the project.
- Pre-existing dead code: mention it; do not delete unless asked.
- Orphans created by your change: remove them.

Every changed line must trace directly to the story. Never run a whole-tree formatter; scope
formatting to the files you changed.

## 4. Goal-Driven Execution

Turn work into verifiable steps before editing:

```
1. <step> → verify: <check>
2. <step> → verify: <check>
```

Bug fix: reproduce first (failing test or failing command), then verify the fix.

## 5. Size and Shape Limits

| Scope | Target | Hard limit |
|-------|--------|------------|
| Source file | ≤ 300 lines | > 400 lines → split |
| Function / method body | ≤ 25 lines | justify in a comment if longer |
| Parameters (Python / Rust / Go) | ≤ 4 | dataclass / struct beyond |
| Parameters (TypeScript / JS) | ≤ 3 | options object beyond |

- No magic numbers: named constants or config.
- Prefer early returns to reduce nesting.
- **Exempt:** tests, docs, generated files, vendored code.

## 6. Code Hygiene

- No debug leftovers (`print(`/`console.log(` used for debugging, `breakpoint()`, `debugger`,
  `dbg!`) in a merged change.
- No commented-out code.
- No secrets in files. Use `.env` (git-ignored) and keep `.env.example` up to date.

## 7. Git Workflow

- Conventional Commits: `<type>(<scope>): <imperative subject ≤ 72 chars>`.
  Types: `feat`, `fix`, `docs`, `test`, `chore`, `refactor`, `perf`, `build`.
  Put the story ID in the body (`Story: US-03`).
- One logical change per commit.
- Stage by explicit path, never `git add -A` (another agent may share the tree).
- Never force-push shared branches. Preserve concurrent work: merge, don't overwrite.

## 8. Make / Test / Document

1. **Make** the story (minimum scope).
2. **Test** it: at least a smoke test or a documented manual check, as `docs/test-plan.md` says.
   Run the tests your change can affect with [SmartTest](https://github.com/RemiPelloux/SmarttyTest)
   (`npx smarttest run`); its pre-commit hook (`npx smarttest hook install`) runs them on every
   commit, and `npx smarttest run --all` runs everything before a release. Never skip a failing test.
3. **Document** it: the README's `Run` section stays accurate, and `docs/decisions.md` gets an
   ADR for any decision that is hard to reverse.

A story is never done on the strength of its spec: it passes `docs/definition-of-done.md`, and the
README's `Run` commands actually work from a clean checkout.

## 9. Clean Dead Code

- Remove unused imports, functions and variables your change created.
- Mention pre-existing issues; do not silently "fix" unrelated debt.
